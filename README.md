# Liberty Tech

Marketing site for **Liberty Tech**, a PC / laptop / mobile repair shop in Gauteng,
South Africa. Single-page, server-rendered, with a runtime-switchable theme and a
contact form that hands off to WhatsApp.

Prices are in ZAR and are shown as "from" ranges. **All copy, services, tiers,
reviews and contact details live in one file — see [Editing content](#editing-content).**

- Live site content: services (8), pricing tiers (3), process steps, reviews, phone numbers, emails
- Themes: Noir, Abstract, Deconstruct — switchable at runtime, persisted per visitor
- No backend required: the contact form validates client-side and deep-links to WhatsApp

---

## Stack

| Layer | Choice |
| --- | --- |
| Framework | [TanStack Start](https://tanstack.com/start) (SSR, file-based routes, Nitro server) |
| UI | React 19, TypeScript |
| Routing | TanStack Router (`src/routes`, generated `routeTree.gen.ts`) |
| Styling | Tailwind CSS v4 (CSS-first `@theme` tokens, no `tailwind.config.js`) |
| Build | Vite 8 |
| Icons | lucide-react |
| Contact form | Plain React state + manual validation (no form library) |

> The workspace also ships pre-wired **Better Auth**, **Postgres/PGlite**, `migrations/`,
> `src/lib/auth`, `src/lib/app-data` and `src/lib/multiplayer`. **None of it is currently
> used by this site** — `src/routes` contains only `index.tsx` and `__root.tsx`, and auth is
> disabled (`.grok/app-env.json` sets `VITE_AUTH_ENABLED: "false"`). It is there so features
> requiring accounts or durable data can be added without new plumbing. Don't delete it
> expecting the build to shrink, and don't wire it in casually.

## Quick start

Requires **Node 22+**.

```sh
npm install
npm run dev
```

Dev server: <http://localhost:8080> (binds `0.0.0.0:8080`).

Or bring the whole thing up with the workspace restart contract:

```sh
sh startup.sh
```

`startup.sh` is idempotent — it exits `0` immediately if `:8080` already answers, otherwise it
stops any stale `:8081` preview and backgrounds `npm run dev`. It is what the platform runs
after a hibernate/revive, so **keep it working**.

## Scripts

| Command | What it does |
| --- | --- |
| `npm run dev` | Dev server on `0.0.0.0:8080` |
| `npm run build` | Production build, then `db:migrate` |
| `npm run typecheck` | `tsc --noEmit` |
| `npm run lint` | ESLint |
| `npm run format` | Prettier, write mode |
| `npm run test` | Node test runner — scripts + auth/app-data unit tests |
| `npm run preview:restart` | Serve the built output on `127.0.0.1:8081` |
| `npm run preview:stop` | Stop that preview |
| `npm run check:auth` | Assert the auth-invariant rules still hold |

`npm run build` runs migrations **only if `DATABASE_URL` is set**; without it, `db:migrate`
logs a skip and exits `0` and the PGlite fallback migrates itself. So a plain clone builds
without provisioning a database.

Always start Vite through `npm run dev` — `scripts/with-app-env.mjs` injects
`.grok/app-env.json` into the environment. Calling `vite` directly skips that wrapper.

## Editing content

**`src/lib/content.ts` is the single source of truth for everything a visitor reads.**
You should not need to touch a component to change a price, a phone number or a review.

Exports, all `as const`:

| Export | Drives |
| --- | --- |
| `site` | Name, byline, tagline, pitch, `phones[]`, `emails[]`, WhatsApp prefill |
| `nav` | Header links (hash anchors into the single page) |
| `values` | The three trust promises |
| `services` | 8 service cards — `from`, `range`, `icon`, `blurb` |
| `tiers` | 3 pricing cards — `includes[]`, `cta`, `featured` |
| `steps` | The 01/02/03 process strip |
| `reviews` | Testimonials — `quote`, `name`, `place` |
| `devices` | Device options in the contact form |
| `waLink(number, text?)` | Builds a `wa.me` deep link with an encoded prefill |

A service or tier's `id` is also the fragment target for `#services` / `#pricing` anchors —
keep it in sync if you rename one.

`src/lib/og/site.json` holds the share-card metadata; `public/og.jpg` is the card image.

component there and dropping it between `<SiteNav />` and `<SiteFooter />`.

## Theming

Three themes are defined in `src/lib/theme.ts`:

| id | Label | Base |
| --- | --- | --- |
| `noir` | Noir | `#080808` (default — no `data-theme` attribute) |
| `abstract` | Abstract | `#110027` |
| `deconstruct` | Deconstruct | `#fbfaf6` (light) |

`ThemeDock` writes the choice to `localStorage` under `liberty-tech-theme` and sets
`data-theme` on `<html>`. To avoid a flash of the wrong theme, `themeInitScript` — a tiny
inline snippet injected in `<head>` before first paint — re-applies the saved theme.
Tokens are CSS custom properties keyed off `[data-theme]`, so a new theme is usually just a
new attribute block in `src/styles.css` plus an entry in `THEMES`.

`setTheme` also syncs `<meta name="theme-color">`, and tolerates blocked storage
(private mode) by applying the theme for the visit only.

## Contact form

`contact-section.tsx` validates name and email in the browser, stores the submission in
`localStorage` (newest 50, key `liberty-tech-leads`), then surfaces a success state whose
primary action is a pre-filled WhatsApp message.

**Nothing is sent to a server.** Leads are not emailed, not stored remotely, and not visible
to the shop — the visitor has to actually tap through to WhatsApp for the enquiry to be
received. That's fine for a brochure site, but it means **"submitted" is not "received."**
To actually capture submissions server-side you need a backend: a `src/routes/api/…` server
function plus either a mail transport or a durable store (`src/lib/db` + `migrations/` are
already wired for the latter).

## Environment

Never create a `.env` file — the platform injects variables at deploy time. Only
`VITE_`-prefixed vars reach the browser.

| Variable | Needed for | Notes |
| --- | --- | --- |
| `DATABASE_URL` | Postgres-backed auth & data | Optional locally; PGlite fallback is used instead |
| `VITE_AUTH_ENABLED` | Toggling the sign-in gate | Read from `.grok/app-env.json` via `scripts/with-app-env.mjs` |

There are no secrets checked in. `src/lib/db.ts` and `src/lib/auth/*` read config through
`src/lib/env.server.ts` and fail loudly rather than falling back to a hardcoded default.

## Deployment

Targets **Vercel**.

- `vercel.json` sets `installCommand: npm install --omit=dev …` — so anything used at
  **runtime** must be in `dependencies`, not `devDependencies`.
- `DATABASE_URL` and auth credentials are injected by the platform. Don't hardcode hosts,
  ports or paths.
- Avoid runtime filesystem writes and Node-only APIs at import time.
- Never put `og:*` / `twitter:card` in `__root.tsx` — the PWA injector overwrites them on
  every HTML response.

### Platform chrome — don't strip it

`grokPwaPlugin()` and `server/middleware/grok-pwa.ts` inject the Grok branding, the share
card, the install tutorial (`?install=1&platform=ios`) and
`https://grok.com/grok-app-builder/extensions.js`. `<PreviewHostBridge />` in `__root.tsx`
lets the live-preview chrome drive the app over `postMessage` and is a silent noop
elsewhere. Removing any of these breaks the hosted preview; they're project settings, not
code — change them in project settings, not by deleting markup.

## QA

Rendered output must be verified in a real browser — a `200` from curl does not mean the page
painted:

```sh
npm run dev
node scripts/browser-smoke.mjs
```

One run audits **desktop and mobile (390×844)** and prints a JSON verdict. Read both
screenshots it writes to `screenshots/` — the JSON cannot catch white-on-white text, overlap
or broken spacing. Confirm the app root has visible content and the console is free of
uncaught errors and failed module loads.

For the production build specifically, dev can render while the deployed build is blank:

```sh
npm run build
npm run preview:restart
node scripts/browser-smoke.mjs --baseline <dev-verdict.json>
```

Watch for `Failed to load module script … MIME type "text/html"`.
